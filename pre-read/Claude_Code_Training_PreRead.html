1From deterministic software to generative AI

  • Your whole stack today (build tools, test suite, CI) is deterministic. Same input, same output, every time.
  • Generative AI is not. It's a different species of system.
  • Think of it like a well-read, fast colleague: usually right, sometimes confidently wrong, always worth a second look before anything ships.

Where "generative AI" sits relative to things you already know:

Three terms, used precisely from here on:

  • Artificial intelligence (AI): any system doing tasks that normally need human judgment. Says nothing about how.
  • Machine learning (ML): learns a function from examples instead of hand-written rules. A spam filter is ML: it classifies, it doesn't create.
  • Generative AI: ML that creates new content: text, code, images. A large language model (LLM) is the text/code version: the engine inside Claude, GPT, and every chat-style assistant.

Claude Code = an LLM + an agent loop:

  • Eyes: reads your files
  • Hands: edits them, runs your build
  • Feedback: sees whether the tests passed

The sections that follow build this up piece by piece, ending with a short tour of Claude Code itself.

Why now, not ten years ago

  • The core ideas (neural networks, the attention mechanism you'll meet shortly) are old, well before ChatGPT.
  • What changed: scale, more training data, more compute, a better architecture (the "transformer").
  • Scale a model up far enough and new abilities show up, sometimes surprisingly quickly: multi-step reasoning, long instruction-following, code in a rarely-seen language.
  • So the pace feels new, but the ideas aren't. The scale needed to make them reliably useful is.

Generative AI beyond text

  • Same idea also builds image, audio, and video generators.
  • Image model: predicts plausible pixels. LLM: predicts plausible tokens.
  • Common thread: generate the next plausible piece, given everything so far.
  • This training is about the text/code case only: the LLM.

The mental-model shift

  • Every tool you've used before this was built to be correct. Run it twice on the same input and it gives the same answer, or it's a bug.
  • An LLM agent is built to be useful instead: a different target. Right most of the time. Confidently wrong sometimes.
  • It gets dramatically better once it can check its own work: run the tests, read the real file instead of recalling it.
  • That's why hands-on practice drills this loop: plan → implement → review the diff → test → verify.
  • Not ceremony: it's the correct way to run a probabilistic tool inside a deterministic engineering process. The Claude Code tour near the end maps each step to a feature.

2How a language model actually produces text

This section pays for itself directly in hands-on practice: model selection, token budgeting, context compaction, and why Claude Code sometimes "forgets" earlier conversation all come straight from the mechanism below.

Tokens, not words

  • A model doesn't read characters or whole words. Text is split into tokens first: a short word, a word fragment, or punctuation.
  • training → one token. tokenization → token + ization. keygen_rotated → three or four pieces.
  • Rule of thumb: 1 token ≈ 4 characters, so 100 tokens ≈ 75 words.
  • Tokenizers differ by model. Anthropic's docs note that Claude 4.7 and later models produce roughly 30% more tokens for the same text than earlier ones, so treat the rule of thumb as approximate.
  • Everything Claude Code measures (context size, /usage, cost) is counted in tokens, not lines or characters.
  • A dense build log burns through budget much faster than the same number of lines of prose.

Embeddings: what a token "means" to the model

  • Internally, a token becomes an embedding: a list of numbers, a point in high-dimensional space.
  • Tokens used in similar contexts land near each other. bug sits close to error, far from banana.
  • Meaning and relatedness become distance and direction in that space: the same idea behind semantic code search.
  • Net effect: the model isn't matching strings, it's reasoning over something closer to meaning. That's why a plain-English bug report can lead it to the right function even with none of the report's wording in your source.

From tokens to a single next guess

  • Your prompt, the conversation, and any file Claude Code has read all become one token sequence.
  • The model's job: given the tokens so far, predict a probability distribution over the next token. That's it.
  • No separate "understanding" step and "generation" step. Predicting the next token well, trillions of times during training, is what produces reasoning, code, and conversation.

The context window: working memory, not long-term memory

  • Everything the model can "see" (instructions, conversation, files it has read) must fit in a fixed token budget: the context window.
  • No separate database on the side. Not in the window = not available to that prediction. Full stop.
  • A long session fills it up. Older content then has to be summarised or dropped to make room.
  • That's exactly what /compact, /clear, and /usage manage.
Engineering analogy The context window behaves like RAM, not disk. Fast and immediately usable, but limited in size and cleared when the session ends. Whatever the model acts on this step must already be loaded into it.

Worked example: where the budget actually goes

  • CI fails → a 400-line build log lands in context. ≈10–15 tokens/line → 4,000–6,000 tokens, before a single real source line is read.
  • + the file it opens to investigate (~2,000 tokens)
  • + a couple of grepped related files (~2,000–4,000 tokens)
  • + the running conversation so far
  • → the window fills from accumulation, not one big paste.
  • /compact then shrinks "400 lines of warning noise" down to "build failed on X, root cause Y, fixed by Z." Budget freed, nothing important lost.

Sampling & temperature: why output isn't identical every run

  • The model doesn't always pick the single highest-probability token: that would be repetitive and bland.
  • Sampling adds controlled randomness (many APIs expose it as a temperature setting). Lower = predictable. Higher = more varied.
  • Day to day you won't be tuning this: you just need to know the variability exists.
  • Same prompt, run twice → two differently-worded (sometimes differently-structured) answers.
  • Treat one run as one sample from a distribution of reasonable answers, not "the" answer.
  • This is why reviewing diffs and requesting targeted refactors matter as habits: verification is built into the workflow because variability is built into the model.
Not the same as learning Run-to-run variability is sampling, not the model updating itself on your conversation. A deployed model's parameters are frozen. What looks like "it's adapting to me" is just more context piling up, gone the moment the session ends. Anything that should persist across sessions goes in CLAUDE.md (or Claude Code's auto memory) instead.

3How a model gets built, and why that matters to you

  • You will never train a model yourself to use Claude Code. This part is here for the consequences of how models are built.
  • Two of them you'll hit in practice: a knowledge cutoff (the model doesn't know recent things) and hallucination (it states something confident and wrong instead of "I don't know").
  • A third explains why a deployed model doesn't learn from your sessions: its weights are frozen.
  • The story behind all three: the model is built in three stages by its maker, before you ever see it.

The three stages in plain terms

An analogy: think of how a new engineer becomes useful on your team. Each training stage has a rough human counterpart:

StageWhat actually happensNew-hire analogyWhat you notice
1. PretrainingThe model reads a huge amount of text and code. At each spot it guesses the next token and is scored on whether it was right. Repeated an enormous number of times.Reading a whole library of books and codebases before day oneFluent code, knowledge of common libraries, general know-how. Also the knowledge cutoff: it stops reading on a date.
2. Fine-tuningFurther training on curated examples of "request → good response". The model learns to answer a request, not just keep writing the text it was given.Onboarding: how to take a ticket, reply in the team's format, decline unsafe requestsIt follows instructions and formats its answers, instead of just continuing your sentence.
3. Feedback training (RLHF)For the same request the model produces several answers; raters rank which is better (human raters, and in some methods AI models following written principles), and it's nudged toward the preferred ones. (RLHF = reinforcement learning from human feedback.)Code-review feedback: "this answer is clearer and safer than that one"Tone, caution, and when it asks a clarifying question versus just proceeding.
"Fine-tuning" here is not something you do You may have heard of companies "fine-tuning a model on their own data". That's a separate, optional thing. The fine-tuning in the table is a standard stage Anthropic completes before release. Using Claude Code needs no custom fine-tuning: your project knowledge reaches the model through its context window (CLAUDE.md, files it reads), not through retraining.
  • Pretraining is where almost all the raw ability comes from. The two later stages shape how it uses that ability.
  • No human labels the pretraining data: the "answer" at each step is simply the token that actually came next in the text.
  • Details like model size or dataset contents don't matter for this training. What matters is that the stages happen once, offline, and finish before release.

What training produces: weights, not rules

  • All three stages adjust one thing: a huge, fixed set of numbers called weights.
  • Together they define one function: "probability distribution over next token, given tokens so far".
  • No rules engine. No lookup table of facts. No "if asked X, answer Y" database anywhere.
  • At inference time (every request you send), the weights are read-only. Running the model doesn't change them.
  • That's the precise sense in which a deployed model doesn't "learn" from you: weights were set once, at the end of training, and stay fixed across every session, every user, until a new version replaces them.

Knowledge cutoff and hallucination, explained

Two behaviours that look like arbitrary bugs, explained by how the model was built:

Knowledge cutoff Factual knowledge is frozen at whenever pretraining stopped reading new data. No library release, CVE, or internal API change after that date, unless it's placed into context at runtime (tool use, MCP).
Hallucination Not a lookup table: always producing the most plausible continuation. Usually correct, because predicting real text correctly is exactly what pretraining rewarded. Under pressure (an obscure API, a name that "sounds right"), fluency and correctness can come apart.

What hallucination looks like in practice

Rarely obviously wrong. Usually a detail that compiles or runs, or almost makes sense:

  • A command-line flag or config option that sounds plausible but doesn't exist in the version you're actually running.
  • A function or API signature recalled from a more common library or version than the one actually in your dependencies.
  • "This function is only called from one place": true of a similar open-source project, not your fork.
  • A confident complexity or performance claim that doesn't match the actual implementation in front of it.
  • All four get far less likely once the model has actually read your file or run your build: the whole point of the agent loop.
  • "Ground it in a tool call, don't trust recall" is a recurring theme across the hands-on exercises.
Practical takeaway Treat an unverified claim about an API, flag, or file path the way you'd treat one from a new teammate who hasn't read the codebase yet: plausible, usually right, worth a quick check before it goes into a commit.

4From language model to agent

  • So far: a system that takes text in, produces text out. A very capable autocomplete.
  • That alone can't read your repo, run make, or open a pull request.
  • Missing ingredient: tool use. The loop built around it turns a language model into an agent.

Tool use (function calling)

  • The model is given a list of "tools": named actions with a defined input, e.g. read a file, run a shell command, search for a pattern.
  • Like handing a new hire a one-page list of commands they're allowed to run.
  • When a tool would help, the model produces a structured request to call it, not just prose.
  • Code outside the model executes the action and feeds the result back in as new input.
  • The model never touches your filesystem directly. It only proposes; the agent harness carries it out.

The agent loop

Wrap one tool call in a loop (reason, act, observe, reason again) and you get the pattern under essentially every coding agent. Claude Code's own documentation describes the same loop as three blending phases: gather context → take action → verify results.

The single most important mental model here "Investigating a bug" isn't recalling your code from memory. It's running the loop: reason → act (grep for callers) → observe (read the matches) → reason again, until it has enough current, grounded information to propose a change. Good tools and relevant context matter more than a cleverer prompt: the loop is only as good as what it's allowed to look at and do.

A worked trace: "the integration test is failing"

You tell Claude Code: "test_connection_timeout is failing, figure out why." A realistic trace through the loop above:

  1. Reason: "I don't know why this test fails yet; I should run it first and see the actual failure, rather than guess from the test's name."
  2. Act: calls Bash to run the specific test with verbose output.
  3. Observe: the test output shows an assertion failure on a timeout value, with a stack trace pointing into a specific source file.
  4. Reason: "The failure is in the connection-handling code; I should read that function before assuming anything about what it does."
  5. Act: calls Read on that file, then searches the codebase (for example with grep through Bash) for other callers of the function to understand blast radius.
  6. Observe: the function's actual timeout default doesn't match what the test expects, and the file's recent git history (another Bash call) shows the default was changed last week.
  7. Reason: "This looks like the test wasn't updated when the default changed. I should propose a fix rather than guess which side is 'correct'; that's a product decision."
  8. Final response: a summary of the root cause, a proposed one-line fix (or a proposed test update), and an explicit note that a human should confirm which value is actually intended before it's applied.
  • Nothing here required knowing your codebase in advance: every fact (the failure, the function, the git history) was pulled in live through a tool call.
  • Watch for this pattern across every hands-on exercise: good output correlates with "did it look at the right things," not "was the prompt clever."

5Prompt engineering: getting the output you actually want

  • The earlier sections gave you the mechanism: the model continues whatever is in its context window, its weights are frozen, and an agent can add real evidence to that context by using tools.
  • So the prompt is the one lever you control on every request: it decides what the model has to work with.
  • Prompt engineering is just that: deliberately shaping the input so the most plausible continuation is also the one you need.
  • Below, the techniques are in the order you'd apply them to a real task. Each one comes back in the hands-on exercises.

1. Write for a smart colleague who has no context

  • Anthropic's own test: show your prompt to a colleague with minimal context on the task. If they'd be confused, the model will be too.
  • The model can infer intent, but it can't read your mind or your team's unwritten conventions.
  • Everything it doesn't see in the context window, it has to guess.

2. Be specific: scope, symptom, location, outcome

The single highest-value habit. Compare vague and specific versions of the same request:

VagueSpecificWhat got added
"fix the login bug""Users report login fails after session timeout. Check the auth flow in src/auth/, especially token refresh. Write a failing test that reproduces it, then fix it."Symptom, likely location, what "fixed" looks like
"add tests for foo.py""Write a test for foo.py covering the case where the user is logged out. Avoid mocks."Scope and a testing preference
"the parser crashes""parse_header() in src/net/parse.c crashes on a zero-length packet. Reproduce it with a failing test, then fix the root cause."Exact function, exact trigger, an order of work
  • Vague prompts aren't always wrong: when you're exploring ("what would you improve in this file?") a loose prompt can surface things you wouldn't have asked about.
  • Use vague to explore, specific to change code.

3. Give context and the reason behind a constraint

  • A bare rule gets followed literally. A rule with its reason gets generalised sensibly.
  • Weaker: "Don't use dynamic allocation."
  • Stronger: "This runs on a target with 64 KB of RAM, so avoid dynamic allocation; use the static pools in pool.h."
  • Point at existing patterns too: "follow how uart_driver.c is structured" beats describing the style in words.

4. Show, don't only tell: examples (few-shot prompting)

  • When the output has a particular shape (commit-message format, log-line style, test layout), a few examples communicate it faster and more exactly than a paragraph of description.
  • This is few-shot (or multishot) prompting. Zero examples is zero-shot.
  • Good examples are relevant (mirror your real use), varied (cover edge cases so it doesn't latch onto an accidental pattern), and about three to five in number.
  • Label them clearly as examples so the model doesn't mistake them for the task input.

5. Structure the prompt so the parts can't be confused

  • When a prompt mixes instructions, background, and pasted material, separate them. XML-style tags (<instructions>, <context>, <example>) are the technique Anthropic recommends; keep tag names consistent.
  • Order matters for long inputs: put the long material (a big log, several files) first and your question or instruction last. Anthropic reports this can improve response quality noticeably on complex, multi-document inputs.
  • For a long document, asking the model to quote the relevant parts first keeps its answer anchored to the text.
  • A one-line role ("You are a code reviewer focused on memory safety") can focus tone and priorities. It matters mostly when you write system prompts; Claude Code already sets its own.
  • State what you want, not just what you don't: "write in plain prose paragraphs" works better than "don't use bullet points".

6. Break big tasks into steps

  • One prompt that asks for ten things tends to do some of them well and others sloppily.
  • Use a numbered list when order matters, or run it as separate prompts, each building on the last result.
  • For code, the pattern that works: explore → plan → implement → commit. Read first, agree the approach, then change files.
  • Skip the ceremony for tiny tasks: if you could describe the diff in one sentence, just ask for it.

7. Supply real evidence, not a description of it

  • "The build is failing" gives the model nothing to reason from. The actual error message gives it a stack trace, a file, a line.
  • Paste the failing output, point at the file (@path/to/file in Claude Code), give a URL for documentation, or pipe data in: cat error.log | claude -p "explain this error".
  • This is the agent-loop lesson applied to prompting: output improves when the model has read the real thing, not recalled something plausible.

8. Define "done" with a check the model can run

  • Without a check, "looks done" is the only signal the model has, so you become the verification loop and every mistake waits for you to notice it.
  • Give it something that returns pass or fail: a test suite, a build exit code, a linter, a diff against expected output.
  • Then it can run the check, read the result, and iterate until it passes, using the agent loop.
  • Ask it to show evidence (the test output, the command it ran), not just to say it worked.
  • Prefer root causes: "fix it and verify the build succeeds; address the root cause, don't suppress the error."

9. Iterate: treat the first prompt as a draft

  • Correct early when you see it drifting. A quick redirect costs less than a long wrong path.
  • If you've corrected the same issue twice and it's still off, the context now holds failed attempts. Start a fresh session with a better prompt that bakes in what you learned: that usually beats a long session of patching.
  • Emphasis (capitals, "CRITICAL", "MUST") is a last resort. Recent models follow instructions closely, so shouting often over-triggers behaviour. Use it on the one line that keeps getting skipped, not on everything.
Prompting vs. context Clever wording can't replace missing information. An exact error message, the right file, and a test to run will beat a beautifully phrased prompt that gives the model nothing to look at. Claude Code adds its own help here: it reads files itself, CLAUDE.md carries standing conventions for every session, and Plan Mode lets you check its understanding before it edits (all introduced later in this document).

6The Claude model family & choosing a model

Hands-on practice covers this fully; this section is just enough to make it land faster.

  • Claude is a family of models, not one fixed model. In Claude Code you pick one by alias: haiku, sonnet, opus, or fable. Each alias points at the latest version of that tier, so specific version numbers change over time.
  • The trade-off is speed and cost versus depth of reasoning.
  • Haiku: fastest and lowest cost, for simple, well-scoped work: a lint fix, a mechanical rename, summarising a log.
  • Sonnet: balanced, the workhorse for most day-to-day coding.
  • Opus: stronger reasoning for complex problems: root-cause analysis, architecture decisions, subtle security questions.
  • Fable: the most capable tier, aimed at the hardest and longest tasks: long autonomous sessions larger than a single sitting. It isn't the default on any plan and can be billed differently, so check your plan before relying on it.
  • Separately, an effort setting (/effort) dials how much the model deliberates before answering, independent of which model you picked. Levels run low, medium, high, xhigh, max, and the default varies by model.

Matching model and effort to task, a starting intuition, refined with real numbers once you're running tasks hands-on:

TaskLikely fitWhy
Fix a lint warning, rename a variable consistentlyHaiku or Sonnet, low effortNarrow, well-specified, low ambiguity: speed matters more than deep reasoning
Implement a small, well-scoped enhancement from a clear specSonnet, medium effortNeeds to follow multi-step instructions correctly but isn't conceptually hard
Diagnose a failing build log with an unclear root causeSonnet or Opus, high effortNeeds to weigh several plausible causes against evidence it gathers; verification matters
Cross-file root-cause analysis in an unfamiliar legacy moduleOpus, high or xhigh effortHigh ambiguity, many interacting pieces, cost of a wrong answer is high
Security vulnerability assessment and patch evaluationOpus, up to max effortSubtle trade-offs, real consequences for getting it wrong. max can overthink, so reserve it for the hard cases
A long, multi-step migration run largely unattendedFableBuilt for sustained autonomous work larger than a single sitting
  • /effort works alongside model choice, not instead of it.
  • Higher effort = more deliberation before answering. Useful for a hard problem. Wasteful for a one-line fix.
  • A useful hands-on exercise: run the same task at two model/effort combinations, compare time, cost, quality, side by side.
Worth previewing: prompt caching Large, unchanging context (a big file already shown, a long system prompt) can be cached: re-sending it next turn is far cheaper and faster. Keeping a session focused, rather than jumping between unrelated files, is both a quality and a cost strategy. Hands-on practice has you inspect this via /usage.

7Claude Code at a glance

  • Everything above applies to any LLM-based agent. This section is the short, Claude Code-specific orientation.
  • Claude Code = the model + the agent loop + a small built-in toolset + a permission layer + extension points.
  • Each piece is taught hands-on in the training, with exercises. Here you only need the name and the one-line idea.
PieceThe one-line idea
Built-in toolsThe core set is small: Read looks at code; Write and Edit change it; Bash does everything else (build, test, git, and on Linux and macOS searching with grep and find; dedicated Grep/Glob tools are the default only on Windows). Web search/fetch and a few orchestration tools (such as spawning subagents) sit alongside. A short, auditable list is what makes the permission layer tractable.
Permission modesAn adjustable boundary between "propose" and "execute". Every tool call passes through it (see the diagram below).
CLAUDE.mdA Markdown file read at the start of every session: build commands, conventions, notes you'd otherwise re-explain. It's context the model reads, not enforcement. Claude Code can also save its own learnings across sessions (auto memory).
Context management/compact summarises, /clear resets for an unrelated task, /usage and the status line show the budget, /rewind restores an earlier checkpoint. Built on the context window idea from earlier.
MCPBuilt-in tools reach only your filesystem and shell. MCP servers connect Claude Code to external systems (CI logs, vulnerability databases, internal APIs); the project config is .mcp.json.
SubagentsSpecialist workers with their own context window, defined in .claude/agents. Heavy work stays out of your main session; only a summary comes back.
HooksScripts that run automatically at lifecycle points (e.g. before a tool call). Deterministic: a pre-tool hook can block a call outright. Use them for rules that must never depend on the model remembering.
Skills & pluginsA skill packages reusable know-how that Claude draws on when relevant. A plugin bundles skills, subagents, hooks, and MCP config so a workflow installs in one step.
Headless mode & Agent SDKclaude -p runs Claude Code non-interactively (CI, scripts). The Claude Agent SDK (Python and TypeScript) exposes the same agent loop as a library for standalone agent applications.

Permission modes: the human-in-the-loop dial

Tool calls have real side effects: an Edit changes a file, a Bash call can run anything. Claude Code makes the boundary between "propose" and "execute" explicit and adjustable:

Plan Mode: the one to know first Claude researches and proposes a plan without editing anything, and changes only begin after you approve it. For unfamiliar code or multi-file changes, that turns "the agent changed something unexpected" into something that can't happen during the planning phase. In current versions, new interactive terminal and VS Code sessions start in auto mode; Manual is a Shift+Tab away. Early hands-on practice has you switch between these modes and watch the approval flow change.

8Common questions & misconceptions

Click to expand. Quick answers here mean hands-on time can go to the actual content instead.

"Isn't this just autocomplete with extra steps?"
  • Autocomplete: next few tokens, current file only.
  • Claude Code: runs the agent loop, reads other files, runs your build, greps callers, checks git history, revises its plan.
  • Related mechanism, different category of tool.
"Is it safe to let something run Bash commands against my repository?"
  • That's what the permission layer is for: every Bash call passes through it.
  • You control how much runs without approval.
  • Plan Mode: nothing executes until you've reviewed a plan.
  • Early hands-on practice: watch this boundary operate before trusting it with real changes.
"Does it actually understand my code, or is it pattern-matching?"
  • What's verifiable is behavioural, not philosophical.
  • Given your files, it traces call graphs, spots inconsistencies, proposes changes consistent with conventions.
  • That needs tracking relationships, not just matching isolated lines.
  • Whether that's "understanding" is a separate question from whether it's useful. This training is about the latter.
"Will this replace the need for senior engineering judgment?"
  • The training's own structure argues no: security and patch exercises have an explicit human-approval checkpoint before any patch is applied.
  • Diff-review exercises have you review and request changes, not accept them wholesale.
  • Judgment about what's correct and what's safe stays with the engineer. The tool speeds up the mechanical part.
"Can it get stuck or go off and do something unbounded?"
  • The loop ends when the model decides the goal is met.
  • In practice, sessions can take a wrong turn or run long.
  • That's exactly why permission modes, hooks, and your ability to interrupt exist: real controls, not theoretical ones.
  • A checkpoint/rewind exercise practices recovering from this.
"If I run this against a legacy codebase with no docs, is it starting from zero like I would?"
  • No, a real advantage over a new hire in the same spot.
  • It can grep the whole codebase, trace every caller, cross-reference git history, in seconds.
  • It lacks your tacit sense of which parts are trustworthy vs. fragile. That's what CLAUDE.md and skills are for: hand it that knowledge explicitly.
"Does my proprietary code get used to train future models?"
  • Governed by your organisation's commercial agreement and admin configuration, not by anything fixed in the architecture here.
  • Ask whoever administers your account.
  • Note: hands-on exercises typically use trainer-provided open-source code, never client proprietary code, so the training itself doesn't depend on the answer.

10Glossary

TermWhat it means here
TokenThe unit text is broken into for the model; roughly 4 characters / ~¾ of a word on average for English prose, often shorter per character for dense code and identifiers.
EmbeddingThe list of numbers a token is converted into internally, a point in a high-dimensional space where related concepts end up near each other.
Context windowThe fixed-size token budget holding everything the model can see for its next prediction: conversation, file contents, tool output. Once full, something must be summarised or dropped to make room.
InferenceRunning the already-trained model to produce output (as opposed to training it); this is what happens every time you send Claude Code a request.
Autoregressive generationProducing output one token at a time, each new token conditioned on everything generated so far: why output streams in progressively rather than appearing all at once.
Temperature / samplingThe controlled randomness in choosing the next token; higher temperature = more varied, less predictable output. Part of why identical prompts can yield differently-worded answers.
PretrainingThe first, largest training stage: next-token prediction over a massive general text/code corpus, the source of most of the model's raw capability.
Fine-tuningA stage of further training, done by the model's maker before release, on curated request → good-response examples. It teaches the model to behave as an assistant rather than a raw autocomplete engine. (Not something you do to use Claude Code.)
RLHF (alignment)Reinforcement learning from human feedback: the final training stage, where people rank candidate answers to the same request and the model is nudged toward the preferred ones, shaping tone, caution, and judgment.
Knowledge cutoffThe date pretraining data collection stopped; the model has no inherent knowledge of anything after it unless that information is supplied at runtime via a tool.
HallucinationA fluent, confident, but factually wrong output, a side effect of the model always producing its most statistically plausible continuation rather than looking facts up.
Prompt engineeringDeliberately shaping what goes into the model's context (instructions, evidence, examples, a way to check the result) so the most plausible continuation is the one you need.
Few-shot promptingIncluding a few worked examples (typically three to five, relevant and varied) of the desired output in the prompt. With none, it's zero-shot.
Verification targetA check the model can run itself (a test, a build exit code, a linter, expected output) so it can iterate until pass/fail says it's done, instead of you being the only check.
Tool use / function callingThe model requesting a structured action (e.g. "read this file") that code outside the model (the agent harness) actually executes and reports the result of.
Agent loopReason → act (tool call) → observe (result) → repeat, until the goal is met and a final response is returned instead of another tool call.
Agentic AIA generative model operating inside an agent loop, with tools and the ability to act across multiple steps, rather than producing a single one-shot reply.
Permission modesSettings for how much Claude Code does before checking with you: Manual (asks before edits and commands), acceptEdits, Plan Mode, auto (a classifier reviews actions instead of you), and bypassPermissions (no checks; isolated containers and VMs only).
Plan ModeA Claude Code permission mode that researches and proposes a plan without editing; nothing changes on disk until you approve the plan.
CLAUDE.mdA Markdown file at your repository root holding project-specific memory (conventions, build commands, notes) that Claude Code loads automatically each session.
MCP (Model Context Protocol)The open protocol Claude Code uses to connect to external systems via tools, resources, and prompts exposed by a standalone MCP server.
MCP InspectorA standalone tool for testing an MCP server's tools/resources/prompts directly, before wiring the server into Claude Code itself.
SubagentA separately-configured agent instance with its own isolated context window, delegated a bounded task by an orchestrator session and returning only a summary.
HookA script Claude Code runs automatically at a defined lifecycle point (e.g. before or after a tool call) to deterministically enforce a rule, independent of model judgment.
SkillPackaged, reusable domain knowledge or process that Claude Code can draw on without it being re-explained each session.
PluginA bundle of skills, subagents, hooks, and MCP configuration, packaged for one-step distribution across a team.
Headless mode (claude -p)Running Claude Code non-interactively from a script or pipeline, with no human watching the terminal: the mechanism behind CI-triggered, automated triage.
Claude Agent SDKA TypeScript/Python library exposing the same agent-loop machinery as Claude Code's CLI, for building standalone, maintained agent applications beyond a CLI invocation.

11Self-check

Thirteen questions. Try to answer each from memory before expanding it: that's a better signal than re-reading would give you.

1. Why does an LLM sometimes give a different answer when you re-run the exact same prompt?

Sampling, not a fixed path. Temperature adds controlled randomness: two runs can diverge even with identical input.

2. What's the practical difference between the context window and a knowledge cutoff?

Context window = this session's working memory, right now. Knowledge cutoff = a fixed training boundary. Cutoff-era info can still enter context at runtime via tools, files, or MCP.

3. Why might a confident, fluent answer about an obscure API still be wrong?

Always producing the most plausible continuation. Fluency and correctness usually align, but can come apart: hallucination. Why verification habits matter.

4. What actually executes a tool call the model requests: the model itself, or something else?

Something else. The model only requests. The agent harness reads the file, runs the command, feeds the result back.

5. In the "failing integration test" worked trace, how did Claude Code learn that the timeout default had recently changed?

An explicit tool call: git history via Bash. Every fact entered through an observed result, not memory.

6. "Fix the login bug" vs. a stronger prompt for the same task: what makes the stronger one better?

It names the symptom, the likely location, and what "fixed" looks like (for example a failing test that reproduces it first). Specific scope and outcome mean fewer corrections.

7. When would you add examples to a prompt rather than write longer instructions?

When the output has a shape that is easier to show than describe, such as a commit-message or log format. Use roughly three to five relevant, varied examples.

8. Why give Claude a test or build command it can run, rather than just asking it to "make it work"?

Without a check, "looks done" is the only signal, so you become the verification loop. With one, it runs the check, reads the result, and iterates until it passes (using the agent loop).

9. Why is Plan Mode considered safer than Manual mode for exploratory work?

It researches and proposes a plan without editing, and changes only start after you approve. That structurally prevents unapproved edits instead of relying on you catching every prompt.

10. Why does a subagent get its own context window instead of sharing the orchestrator's?

So heavy work (e.g. a full build log) doesn't eat the orchestrator's budget. Only a summary crosses back.

11. What problem does MCP solve that the core built-in tools (read, edit, search, shell) don't?

Built-in tools only reach your local filesystem and shell. MCP reaches external systems: CI logs, vuln databases, internal APIs.

12. Where would you encode a rule that must never depend on the model remembering it correctly?

A hook: a deterministic script at a lifecycle point, not a hope that the model remembers. (CLAUDE.md is context the model reads, not enforcement.)

13. Why doesn't "it's agentic" mean "it operates without any human checkpoint"?

Agentic = plans and acts across steps on its own. It doesn't mean every step skips review by default: see the permission modes and the human-approval checkpoints in the security exercises.

That's the full foundation Arrive at your first hands-on session with this vocabulary loaded. Installing Claude Code and watching the agent loop and permission modes in action will confirm what you already understand, not introduce it from zero.
